## 2026-05-19 — UI Tweaks: Tailwind v4 Border Cascade, Navbar, Tab Title

**Tailwind v4 left-border cascade conflict.** The `LayerCard` component in `PipelineResult` was given per-layer accent colors via Tailwind utility classes (`border-l-rose-400` etc). In production the borders were invisible — the left edge stayed the default `zinc-200`. Root cause: Tailwind v4 generates a stylesheet where the `border-color` shorthand rule (from `border-zinc-200`) appears *after* the `border-left-color` longhand rule (from `border-l-rose-400`) in cascade order. Shorthand always overwrites longhand when specificity is equal and source order is later. This is a known Tailwind v4 behavior change — v3 generated longhand and shorthand in the same rule block so there was no conflict. Fix: changed `LayerCard`'s API from `accentCls: string` (a Tailwind class string) to `accentColor: string` (a CSS hex value), applied via `style={{ borderLeftColor: accentColor }}`. Inline styles have higher specificity than any stylesheet rule so the cascade never wins. Layer colors: L1 = `#fb7185` (rose-400), L2 = `#fbbf24` (amber-400), L3 = `#a78bfa` (violet-400).

**Navbar redesign.** The original header was a flat row — brand name, then email, then sign-out form. No visual grouping, no hierarchy. Redesigned to a 3-zone layout: Brand (`flex-1`) | Env+Spec (centered, `gap-3` between selectors with a vertical divider) | Account (`flex-1 justify-end`). The account zone became an `AccountMenu` component: an avatar button showing the user's email initial (white text on `bg-zinc-800`), with a popover dropdown containing the full email address and the sign-out form. Outside-click to dismiss uses a `useRef` on the wrapper div and a `document.addEventListener('mousedown')` in `useEffect`, cleaned up in the effect's return. The `EnvSelector` and `SpecSelector` were also cleaned up: removed the custom `GlobeIcon` and `BookIcon` SVG components and replaced with plain `<span>` labels (`text-[11px] font-semibold uppercase tracking-wider text-zinc-500`) reading "Env" and "Spec". Text labels are more legible than abstract icons and require no maintenance.

**Browser tab title.** `apps/web/app/layout.tsx` still exported the scaffolded `"Create Next App"` metadata. Fixed to `title: "APILens"` with description `"API debugging pipeline — validation, heuristics, and AI triage in one view."`.

## 2026-05-18 — Mental Model Pivot: Pipeline-First Design

**The pivot.** The previous UI was response-first: the HTTP response (status code, headers, body) was the main event and the three analysis layers were commentary below it. This is the Postman mental model — get the envelope, then look at the contents. APILens is for engineers who want the X-ray, not the envelope. The three analysis layers ARE the product; the raw HTTP response is subordinate output. Rebuilt the result panel entirely around this insight.

**`PipelineResult` component.** Created `components/pipeline-result/index.tsx` to replace `ResponseViewer` as the primary result panel. Architecture: a `PipelineSummary` strip at the top showing three colored status dots (green = pass, amber = warning, red = blocked, zinc = skipped) plus a one-line summary sentence derived from whichever layer blocked or from total pass count. Below that, three `LayerCard` panels — L1 Validation, L2 Heuristics, L3 AI Triage — each collapsible, each with a colored left-border identity (rose / amber / violet). Below a `— Response —` divider, the HTTP response section (status badge, latency, response body via `JsonBody`). The layered structure means engineers see all three analysis results immediately without scrolling past a giant JSON body.

**L1 rule checklist.** Layer 1 has five named rules — SSRF Protection, URL Validation, Content-Type, JSON Body, Schema Validation — each rendered as a pass/fail/skip row with a status icon. The `skip` state required careful thought: `validate.ts` uses early returns (invalid URL → return early; SSRF blocked → return early before CT/JSON checks), which means some rules are never evaluated, not "passed." The frontend mirrors this with `getL1RuleStates()`: if `INVALID_URL` or `DISALLOWED_PROTOCOL` appears in `layer1Flags`, all subsequent rules are marked `skip`; if `SSRF_BLOCKED` fires, content-type/JSON/schema are `skip`. This makes "not reached" visually distinct from "evaluated and passed" — a skip after a block means the pipeline stopped there, not that the request was clean on those axes.

**L3 explanation formatting.** The raw Groq explanation is unstructured prose. Added `renderExplanation()` — walks the string and wraps substrings matching known patterns in styled violet `<code>` pills: quoted strings, HTTP methods (GET/POST/PUT etc.), and 4xx/5xx status codes. No full markdown parser — just targeted pattern matching for the tokens that engineers actually scan for in API error messages.

**`JsonBody` extracted.** The JSON tokenizer and collapsible body display (50-line collapse with "Show all N lines" expand) were inside `ResponseViewer`. As `ResponseViewer` was stripped down to an export stub, `JsonBody` was made a named export so `PipelineResult`'s `ResponseSection` could import it. `response-viewer/index.tsx` now contains only the tokenizer and `JsonBody` — no layer cards, no status rendering, no warning panels.

## 2026-05-17 — Bug Fix: INVALID_JSON_BODY Stale Result

**Symptom.** Typing `{name: bad json}` (unquoted key) into the body field and sending — the previous request's full pipeline result stayed on screen. The L1 JSON Body rule showed a green checkmark instead of a blocked state.

**Root cause 1 — `setResult(null)` behind `setLoading`.** The state-clearing sequence in `handleSend` was: check empty URL → `setLoading(true)` → `setError('')` → `setResult(null)`. The JSON parse attempt happens before `setLoading(true)`, and on a parse failure the function returns early before ever reaching `setLoading`. So `setResult(null)` never ran, and the stale result from the previous request stayed in state.

**Root cause 2 — `hasJsonCt` gate on the blocked path.** The error-recovery path was guarded: `if (hasJsonCt) { setResult(blocked) } else { setError('...') }`. With auto-inject enabled (the engine adds `Content-Type: application/json` when there's a body), users who hadn't manually set the header had `hasJsonCt = false`, so invalid JSON without an explicit header called `setError` instead of `setResult` — which never cleared the old result.

**Fix.** Moved all three state clears (`setError('')`, `setResult(null)`, `setExplainError('')`) to before the JSON parse attempt so they run unconditionally regardless of which early return fires. Removed the `hasJsonCt` gate: invalid JSON always creates a blocked pipeline result with `INVALID_JSON_BODY` in `layer1Flags`. This is correct because the engine always auto-injects `Content-Type: application/json` before running validation, so the JSON check always runs for POST/PUT/PATCH with a body.

## 2026-05-14 — Bug Fixes: Explain Bar and Content-Type Warning

**Bug 1 — Explain bar missing on 4xx/5xx.** The `AIPanel` component in `ResponseViewer` had an inverted guard: `if (!isError) { return <ExplainBar /> }` — meaning the bar only rendered on success responses. On error responses where `aiExplanation` was null (e.g. no `ANTHROPIC_API_KEY` configured), the component fell through to `return null`. This was backwards from the design intent: 4xx/5xx are exactly the responses users most want to explain. Fix: removed the `!isError` guard so the bar renders whenever `ai` is null regardless of status code. The message now adapts — error responses show "AI explanation unavailable — try manually?" (auto-trigger ran but had no key) and success responses keep "Want to understand this response?".

**Bug 2 — Content-Type mismatch warning never surfaced.** The DEVLOG from Phase 2 describes a validator that emits a `MISSING_CONTENT_TYPE` warning when a POST has a body but no Content-Type header. The warning was implemented correctly in the backend but never reached the UI because the frontend was silently injecting `Content-Type: application/json` into `headerMap` before sending to the proxy: `if (parsedBody !== undefined) headerMap['Content-Type'] = 'application/json'`. The backend's `validateRequest` therefore always saw a Content-Type present and never flagged it. The UI even showed a grayed-out "auto" row in the headers tab as a visual confirmation of this behavior — it looked like a feature but was masking a validator that could never fire. Fix: removed the auto-inject line entirely. The backend now sees exactly what the user configured and surfaces the warning as an amber banner in the response viewer when Content-Type is missing. The "auto" display row was replaced with an amber hint banner ("No Content-Type set — servers may reject or misparse this body.") with a one-click "Add" button that inserts `Content-Type: application/json` into the user's actual header rows — so the validator fires correctly if ignored, and adding it is still one click if the user wants to fix it.

## 2026-05-14 — CI/CD, Test Suite, and Repo Hygiene

**GitHub submodule bug.** Pushed the project to GitHub and found the `apilens/` folder was unclickable — displayed as a grayed-out folder icon pointing to a commit hash. Root cause: Git had the folder tracked as a gitlink (mode `160000`) — a broken submodule reference with no `.gitmodules` entry to back it up. This happens when a nested `.git` directory exists at some point in the folder's history, causing Git to record it as a submodule commit instead of a regular tree. Fix: `git rm -r --cached apilens` to remove the gitlink, then `git add apilens` to re-add all 63 files as normal tracked content. The distinction between mode `160000` (gitlink) and `040000` (tree) is invisible to `git status` once the `.git` directory is gone — you have to check with `git ls-tree HEAD apilens` to see it.

**GitHub Actions.** Set up three workflows. (1) **CI** (`ci.yml`): runs on every push to `main` and every PR — installs pnpm deps, runs tests, compiles TypeScript, and lints. The first attempt used `pnpm/action-setup@v4` with `version: latest`, which pulled pnpm v10. pnpm v10 requires Node 22, but the runner had Node 20, and the mismatch threw `ERR_UNKNOWN_BUILTIN_MODULE: node:sqlite` during setup. Fix: pin to `version: 9`. (2) **Dependency Review** (`dependency-review.yml`): uses GitHub's official `actions/dependency-review-action` to scan new packages introduced by PRs for known CVEs — fails on `moderate` severity and posts a summary comment on the PR automatically. (3) **Docker Compose** (`docker.yml`): only triggers when `docker-compose.yml` changes (no point running it on every commit). Validates the compose syntax with `docker compose config --quiet`, spins up Postgres and Redis, health-checks both with `pg_isready` and `redis-cli ping`, then tears everything down. Since the project has no custom Dockerfiles (only upstream images), the workflow is purely about verifying the infra config is valid.

**Test suite.** The project had zero tests. Added Vitest (v2) as the test runner for the API — chosen over Jest because it handles TypeScript natively without Babel config, and the monorepo's CJS tsconfig would have required extra Jest transform setup. Wrote 60 tests across three files covering the core logic modules. `validate.test.ts` (22 tests): covers every SSRF-blocked IP range (loopback, RFC1918, CGNAT, link-local, IPv6 unique-local), disallowed protocols (file://, ftp://), malformed URLs, and Content-Type warning edge cases including case-insensitivity of the header key and GET-with-body being correctly ignored. Mocking `dns.promises.lookup` required `vi.hoisted()` — Vitest hoists `vi.mock()` calls above all imports at transform time, so any variable referenced inside the mock factory must also be hoisted; a plain `const mockLookup = vi.fn()` at the top of the file is not hoisted and causes a `ReferenceError` at setup. `heuristics.test.ts` (20 tests): mocks the Redis client entirely via `vi.mock('../redis')` and tests latency anomaly detection (exact threshold at 2x average, minimum 5-sample guard, multiplier value in the message), consecutive 401 counting and reset behavior, all four known error pattern regexes, and Redis crash resilience — the catch block must return `[]` so a Redis outage never crashes the proxy. The mock for this file also required `vi.hoisted()` for the same reason. `validator.test.ts` (18 tests): pure function tests, no mocking needed — covers path parameter matching (`/users/{id}` regex), server base path stripping before spec lookup, required field validation, type mismatches, the OpenAPI 3.0 nullable-to-JSON-Schema conversion (`nullable: true` → `type: ['string', 'null']`), and the response validator's fallback behavior when endpoint or status code has no spec entry.

**ESLint for the API.** The API had `"lint": "eslint src"` in `package.json` but no ESLint config and no ESLint installed — the script would have errored immediately if run. Added `eslint@9` and `typescript-eslint@8` (the unified flat-config package that bundles both the plugin and parser) to devDependencies, and created `eslint.config.mjs` using `tseslint.configs.recommended` with two overrides: `no-explicit-any` as a warning (not an error, since the codebase casts JSON blobs through `unknown`) and `no-unused-vars` as an error with `^_` exemption for intentionally unused parameters.

**TypeScript build fixes.** The CI build step (`pnpm build`) ran `tsc` without first running `prisma generate`. The Prisma client — including the `Prisma` namespace with `JsonNull`, `DbNull`, and `AnyNull` — is generated code that lives in `node_modules` and is NOT committed to git. Without generation, `Prisma.JsonNull` (used in `ai.ts` to filter cached AI results) doesn't type-check. Fix: changed the API's build script from `"tsc"` to `"prisma generate && tsc"` so generation always runs before compilation. `prisma generate` doesn't need a live database connection — it only reads the schema file — so this works cleanly in CI. Second error: `proxy.ts` had a `.catch(err =>` where `err` was implicitly typed as `any` under `strict: true`. Fix: explicit annotation `(err: Error)`.

**React hook lint violations.** The web lint step flagged `use-collections.ts` and `use-environments.ts` for calling `setState` synchronously inside `useEffect` without batching. Both hooks initialize state from `localStorage` in an empty-dependency `useEffect` — the standard Next.js pattern for reading browser-only APIs without SSR crashes (lazy `useState` initializers run on the server too and throw `ReferenceError: localStorage is not defined`). In `use-environments.ts`, both `setEnvironments` and `setActiveEnvIdState` are wrapped together in a single `startTransition` call, which also batches them into one render instead of two — a minor perf improvement over the original.

**Other.** Added `.env.example` documenting all six required environment variables (`DATABASE_URL`, `REDIS_URL`, `ANTHROPIC_API_KEY`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `PORT`). Added a 30-second `AbortSignal.timeout(30_000)` to the `fetch` call in `engine.ts` — without it, a hung upstream server would hold the request open indefinitely, blocking the Express worker.

## 2026-05-13 — Phase 4: Layer 3 AI Triage

**Architecture.** Added the third and final analysis layer — AI-powered explanation via the Anthropic Claude API. The flow is: every proxied request now writes a `RequestHistory` row to Postgres (with `layer1Flags` and `layer2Flags` stored as JSON). ## 2026-04-24 — Phase 1: Core Request Runner (proxy engine + UI)

**Proxy engine.** Built `src/proxy/engine.ts` in the Express backend — a pure function that accepts `{ method, url, headers, body }`, forwards the request to the upstream API using Node's native `fetch`, and returns `{ statusCode, headers, body, responseTime }`. Kept it separate from the route file deliberately: the route is just the HTTP interface, the engine is the logic. This matters later because Layer 1 and Layer 2 will wrap around this same function. The non-obvious detail was hop-by-hop headers — HTTP headers like `Connection`, `Transfer-Encoding`, `Keep-Alive`, and `Host` describe the TCP connection itself and must be stripped before forwarding or they confuse the upstream server. Also read the response body as text first and attempted `JSON.parse` — this means the frontend gets a structured object for JSON APIs and a plain string for everything else (HTML error pages, plain text) without crashing on either. Wired it up as `POST /api/proxy/request` in `src/routes/proxy.ts`, replacing the hardcoded hello-world. Verified with `curl` against `httpbin.org` before touching the frontend — confirmed GET and POST both worked with correct body forwarding.

**Request builder UI.** Built two components: `RequestBuilder` (owns all state) and `ResponseViewer` (pure display, receives result as a prop). The request builder has a method selector, URL bar with Enter-to-send, and a tabbed panel for Headers and Body. Headers are stored as an array of `{ key, value }` objects — not a plain object — because the UI needs empty rows and the ability to add/remove individual rows. Auto-expanding rows: when you start typing in the last header row, a new empty row appears automatically (the Postman pattern). Body is validated as JSON client-side before the request fires — better to catch a malformed body immediately than get a confusing 400 from upstream. The response viewer color-codes status codes: green (2xx), blue (3xx), orange (4xx), red (5xx). The dashboard page stays a Server Component that handles auth, and drops `RequestBuilder` in as a client island — auth logic on the server, interactivity on the client.

**Collections (localStorage).** Decided against Postgres-backed collections for now — jumping straight to DB adds backend routes, Prisma queries, and API auth before the UX is even proven. **What broke (collections).** After loading a saved request, the headers tab showed no rows at all — not even an empty placeholder. The response not persisting after loading a saved request is intentional — the tool saves what you sent, not what came back.

## 2026-04-24 — Phase 2: Layer 1 Validation

**Architecture.** Added a validation layer that sits between the HTTP route and the proxy engine. The route calls `validateRequest()` first; if any issue has `severity: 'error'` the request is blocked with a 400 and never reaches the engine. Issues with `severity: 'warning'` are collected and merged into the result that the frontend receives. The engine itself also inspects the response and can emit its own warnings (response CT/body mismatch). This two-severity model is deliberate: errors represent things that are definitely wrong or dangerous, warnings represent things that are probably wrong but worth forwarding anyway.

**SSRF protection.** SSRF (Server-Side Request Forgery) is the attack where you trick a backend into fetching a URL it shouldn't — most famously the AWS instance metadata endpoint at `169.254.169.254`, which returns IAM credentials if hit from an EC2 instance. The fix is to resolve the hostname via DNS before forwarding (`dns.promises.lookup` with `all: true` to get every address the hostname maps to), then check every resolved IP against blocked ranges: loopback (`127.x.x.x`, `::1`), RFC1918 private ranges (`10.x`, `172.16-31.x`, `192.168.x`), link-local (`169.254.x.x`), CGNAT (`100.64-127.x`), and IPv6 ULA/link-local. If any resolved address is in a blocked range, the request is rejected before any network connection is made. The IP comparison is done by converting dotted-decimal to a 32-bit unsigned integer and checking inclusive ranges — no library needed.

**Content-Type mismatch warning.** When a POST/PUT/PATCH request has a body but no `Content-Type` header, many servers either reject the request (415) or silently misparse it. The httpbin test made this concrete: without the header, the upstream received `Content-Type: text/plain;charset=UTF-8` (Node fetch's default) instead of `application/json`. The validation layer detects this and emits a warning that flows through to the UI, where it appears as an amber banner above the response.

**Response inspection.** The engine now checks whether a response that claims `Content-Type: application/json` actually contains parseable JSON. This catches a common misconfiguration where a load balancer or CDN returns an HTML error page with the wrong content-type header. If the body fails to parse and the content-type claimed JSON, a warning is added to the result.

**Frontend wiring.** Added a `ValidationIssue` type to the frontend's `ProxyResult` interface. Fixed a latent bug in `send()`: previously, backend 400s and 502s were passed straight to `setResult`, which would crash the response viewer since those responses don't have `statusCode`/`headers`/`body`. Now `res.ok` is checked first — non-OK responses go to `setError` instead. The response viewer shows an amber warnings panel above the status bar whenever `result.warnings` is non-empty; it's invisible when there are no warnings so clean requests don't have visual clutter.

## 2026-04-24 — Phase 3: Layer 2 Heuristics

**Architecture.** Added a heuristics module that runs after every successful proxy response. Unlike Layer 1 (which runs before the request and can block it), Layer 2 only observes and annotates — it never stops a request. It reads and writes to Redis for session memory, then appends its hints to the same `warnings` array the frontend already renders. Redis errors degrade silently so a Redis outage never takes down the proxy.

**Shared Redis client.** Created `src/redis.ts` as a single shared `ioredis` instance with `lazyConnect: true` and `maxRetriesPerRequest: 1`. Lazy connect means the process doesn't fail to start if Redis is unreachable — it only connects on first use. One retry means a blip doesn't cascade into a hung request. The error handler logs to console without throwing.

**Latency anomaly detection.** Every response time is pushed into a Redis list keyed by `latency:{METHOD} {host}{pathname}` (query params stripped so `/users?page=1` and `/users?page=2` count as the same endpoint). The list is capped at 50 entries with `LTRIM` and given a 24-hour TTL. After recording, we read back all entries: index 0 is the value just pushed (current), everything after is history. If there are at least 5 total samples (so we have at least 4 historical readings) and the current response time exceeds 2x the historical average, a warning fires. The 5-sample minimum prevents false positives on the first few requests — you can't call something anomalous without a baseline. Endpoint normalization strips query params deliberately: latency patterns belong to the route, not to a specific query string.

**Consecutive auth failure detection.** A Redis counter keyed by `auth_fails:{endpoint}` is incremented on every 401 and deleted on any non-401. An expiry of 1 hour means the counter auto-clears if you walk away. The warning fires from the 3rd consecutive 401 onward and includes the count in the message so you can see it escalate. Deleting (not just resetting to zero) on success means a 200 fully clears the streak — if you fix your token the warning disappears immediately.

**Known error pattern matching.** Four regex patterns run against the stringified response body after every request: invalid API key, rate limiting, expired token, connection refused. Only the first match fires (no double-warnings per response). The patterns are case-insensitive and allow for common variations (`rate-limit`, `rate limit`, `rate_limited`). This catches the most common "why is this failing" cases without needing spec knowledge.

**What broke.** Nothing in the build — both TypeScript checks passed clean. The more interesting thing was realizing that `lpush` puts the new value at index 0, not the end, which means the "current" reading is always `values[0]` and the history is `values.slice(1)`. Getting this backwards would have compared the current response against an average that included itself, slightly dampening the anomaly signal. The test confirmed the fix: six consecutive fast GET requests, no false flags.

**Environments.** Added a `useEnvironments` hook (also localStorage-backed) and an `EnvSelector` component in the header. Environments have a name, a color (from a fixed palette), and a list of `{ key, value }` variable pairs. Variable substitution (`{{VAR_NAME}}` → actual value) happens in `interpolate()` inside `RequestBuilder` at send time only — the raw template strings in state are never mutated, so you always see what you typed and can switch environments without losing the template. The `EnvSelector` lives in the header inside `Workspace` so env state is co-located with the request builder that consumes it.

**Environment UX polish.** First pass felt hollow — no feedback after adding variables, no visual hierarchy in the modal, no way to peek at variables without opening settings. Did two rounds of UX fixes. Round 1: moved the env selector into the header bar, added a colored left-border accent on the dropdown to reflect the active environment's color, structured the modal with a proper header. Round 2 (from a detailed fix spec): (1) the Create button stays gray and says "Create" when the name field is empty, turns green and says "Save & Add Variables" the moment the user starts typing — this makes the intent of the button obvious; (2) auto-save indicator — a "✓ All changes saved" message flashes for 2s at the bottom of the modal on variable field blur, and the row that was just saved gets a green highlight for 500ms; (3) gray section headers ("Existing Environments" / "Create New") replaced the undivided white box, and a "Done" button in the footer replaced the corner X; (4) color swatches let users assign Red for Prod, Yellow for Staging, etc., with a left-border on the dropdown reflecting the active env color; (5) an eye icon next to the dropdown shows a hover tooltip listing the top 5 variables in the active environment ("+N more" if there are more), so you can verify context without opening the modal. The timer refs for the save/highlight animations used `useRef<ReturnType<typeof setTimeout> | undefined>(undefined)` — TypeScript requires an explicit initial value when the type doesn't include `undefined` implicitly.
